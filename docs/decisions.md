# Decisions

| Date | Decision | Why |
|---|---|---|
| 2026-11-25 | Wallet: `smart-account-kit` (OpenZeppelin smart accounts), with `passkey-kit` as the fallback | Current Stellar guide; Launchtube-era tooling is retired |
| 2026-11-25 | Fees: OpenZeppelin Channels testnet relayer, called only from our server | Launchtube is retired; Channels blocks browser calls; the API key must stay server-side |
| 2026-11-25 | One split contract per user, constructor-initialised, no admin, no upgrade | Users' funds never mix; nothing can front-run init; no one but the owner moves money |
| 2026-11-25 | Pay flow: the client calls `deposit(from, amount, invoice_ref)` in USDC first. Then "pay in XLM" adds a classic path payment to the client's own account before the deposit (two signatures) | Classic payments cannot reach contract addresses, and a plain transfer does not run the split. Joshua chose this over a Soroswap route |
| 2026-11-25 | Invoice reference is a contract argument and appears in the `split` event; one deposit per invoice | Soroban transactions cannot carry memos, and a muxed id is not readable inside the contract |
| 2026-11-25 | Naira rate: CBN official rate, labelled with its source, behind an oracle-shaped interface | Reflector's testnet FX feed has no NGN |
| 2026-11-25 | Stamp duty at cash-out: show a sourced notice, deduct nothing | The rule puts the duty on the transferee (the token buyer on a cash-out). Joshua chose inform, don't deduct |
| 2026-11-25 | Withholding tax is not modelled | No source gives the rate for professional fees paid in crypto |
| 2026-11-25 | Cash-out auth: SEP-45 (contract accounts), on testanchor.stellar.org | The user's wallet is a contract account; the test anchor lists SEP-45 |
| 2026-11-25 | Core flow (features 1 to 4) end to end on testnet by Sat 28 Nov | Joshua kept the card's date. Submission is Tue 1 Dec; the Lagos showcase is Sat 5 Dec |
| 2026-11-25 | Invoices are opened on chain by the owner with an exact amount; one exact payment settles them | Codex r1: any payer could mark an invoice paid with 1 stroop and block the real payment |
| 2026-11-25 | `/api/relay` enforces a sponsorship policy: `{func, auth}` only, address-signed auth only, deploys of allowlisted wasm, named functions on allowlisted wasm or USDC `transfer`, checked through every auth tree and through a wallet's `execute`; per-IP and per-instance burst limits | Codex r1 and r2: the relay was an open sponsorship endpoint, and a wallet's `execute` could reach any contract. Source-account auth would make the relayer itself the signer. Forwarded IPs are trusted only on Vercel or behind a configured proxy. The limits are a per-process burst control, not a global budget: a shared quota comes with the database |
| 2026-11-25 | Tax engine requires proven coverage per account, a same-day sourced CBN quote, an explicit income scope, and offset-bearing timestamps | Codex r1: freshness is not completeness; a stale or unsourced quote gave a number; unclassified income was silently excluded |
| 2026-11-25 | Statutory FX quote is structured (provider, pair, date, sourceUrl, retrievedAt) and checked against the rules: provider CBN, URL on cbn.gov.ng, USD/NGN for USDC (assumes 1 USDC = 1 USD, labelled) | Codex r2: a free-form source label let a made-up rate pass as official. The engine still trusts the rate adapter for the number itself |
| 2026-11-25 | Relay sponsors only Caracal's own code and signers: every payer, owner and signer is a passkey wallet (or the kit's shared deployer deploying one); split contracts must hold USDC and be wallet-owned; wallets must use the WebAuthn verifier and no policies; a deployment must be explicitly authorised | Adversary r2a: a split over an outside token would run outside code on Caracal's fees, and a classic `from` could be authorised implicitly by the relayer's own account. The CLI-owned demo split is therefore not sponsored; the CLI pays its own fees |
| 2026-11-25 | Known limit: the relay recognises a passkey wallet by its wasm hash only. A wallet deployed outside the relay (its deployer pays) with a non-WebAuthn verifier would still pass as a wallet, and its `__check_auth` would run that verifier on sponsored fees | Checking a wallet's signers means reading its signer storage per call. Bounded today by the rate limits and testnet; to revisit with the indexer, which will know every wallet Caracal itself deployed |
| 2026-11-26 | The relay builds, simulates (signatures enforced) and signs each sponsored transaction itself with a relay-only testnet account (`RELAY_SOURCE_SECRET`), and allows only Caracal's wasm (passkey account, split, WebAuthn verifier) in its footprint. Everything except creating a wallet goes to OpenZeppelin Channels (`CHANNELS_API_KEY`) as that signed transaction for a fee bump only; creating a wallet from the shared deployer (every signer a G address) still goes to SDF's proxy as `{func, auth}`, since a deploy names its exact code hash and no passkey wallet's code runs. A deploy authorised by a passkey wallet runs that wallet's `__check_auth`, so it is pinned like a call. Without the Channels key, contract calls are refused | Codex r3: a cached wasm hash let an owner-upgraded wallet run other code at the sponsor's expense. Soroban runs only code in the declared footprint, so pinning the footprint closes the gap between check and execution; enforced simulation also refuses junk auth before it reaches the sponsor. SDF's public proxy refuses pre-built contract calls (tested 2026-11-26: "Only createContractV2 deployments are allowed"), hence Channels with our own key |
| 2026-11-26 | Known limit: sponsored submissions are serialised per server process, because they share one source account's sequence numbers. Several server instances need one source account each. If the RPC lags behind the last confirmed transaction, the next one fails with a bad sequence and the user is asked to retry; it is never run twice. The relay account holds only friendbot XLM and is never a signer on user funds | Simplest correct option for testnet; a pool of source accounts comes with the shared quota |
| 2026-11-26 | Channels is called through OpenZeppelin's official client, `@openzeppelin/relayer-plugin-channels` pinned at 0.21.1, not a hand-written HTTP call. Changed test expectation: an empty (204) answer was at first still passed on for wallet creation (SDF proxy; superseded below, after adversary r3h), but on the payment path any Channels answer without a transaction hash (empty, HTML, unreadable, timeout) becomes a 502 that tells the user to check their activity before trying again | Joshua's decision on Codex r3: a maintained integration we update deliberately (a pinned version does not follow API changes by itself). Without a hash nobody can tell whether a payment happened, so passing on an empty 204 would hide that. Tests run the client's real code against a local stand-in for Channels (`apps/web/test/relay-channels.test.ts`), including that it submits the exact signed XDR. Proven live on testnet 2026-11-26 (`apps/web/scripts/live-channels-payment-path.mjs`): a passkey wallet deployed its own split contract through the relay and Channels, tx `81842cbc7b1a31b0492eca57c954e865a0d4ddd08f879054cb864d8e05e349a4`, a fee bump paid by Channels around the relay account's signed transaction |
| 2026-11-26 | A Channels error says "nothing was sent" only for codes the plugin (0.21.1) raises before sending; `ONCHAIN_FAILED` says nothing changed; `WAIT_TIMEOUT`, any other code or none tells the user to check their activity before trying again. SDF proxy refusals show a fixed message and a code-shaped code, never the proxy's wording. Sign-out falls back to ending the session in this browser only when Supabase cannot be reached, and reports failure if the session survives | Adversary r3b: `WAIT_TIMEOUT` ("It may still submit") was shown as "refused", inviting a double payment; and an offline sign-out left the previous person signed in while the page said they were out. The code list must be re-checked on any plugin upgrade |
| 2026-11-26 | Only a Channels answer with status `confirmed` counts as a sponsored transaction done; any other status with a hash (expired, canceled, or a new one) is a 502 telling the user to check their activity. An unusable RPC URL or Supabase URL gives the documented "not set up" answer instead of a crash; sign-out ends the session even if storage refuses; a failed load of the wallet kit is retried on the next use | Adversary r3c: plugin 0.21.1 throws only for `failed`, so an expired payment was shown as a success; an http RPC URL and the unedited Supabase placeholder crashed the relay and the sign-in callback |
| 2026-11-26 | Wallet creation through SDF's proxy also counts as done only with status `confirmed` and a 64-hex hash, and the answer is rebuilt from those fields. The Channels call has an overall deadline (`CHANNELS_TIMEOUT_MS`), not only the client's idle timeout. Sign-out ends the session at once, alongside a wallet disconnect bounded to 5 s. The wallet page offers create or connect only after it knows the signed-in account | Adversary r3d: an expired wallet creation showed as a connected wallet; a Channels answer trickling in forever held the relay's queue; a stuck wallet kit blocked sign-out; and (its suspicion) a failed sign-in check still offered create or connect, which could leave the previous person's owner binding on a new wallet |
| 2026-11-26 | Wallet creation through SDF's proxy uses the same split as Channels: only a code known to be raised before sending says "nothing was sent"; any other refusal, a network failure or a timed-out answer says the outcome is unknown and asks the person to reload and check with Connect before creating another wallet. `CHANNELS_TIMEOUT_MS` accepts 1 to 600000 ms, anything else means 60000; every timer is capped at the largest delay setTimeout honours. Changed test expectation: r3b's proxy-refusal tests now expect the outcome-unknown wording | Adversary r3e: "refused, try again" after a proxy timeout led to a second passkey and an orphan wallet; a huge timeout value made every payment fail at once (Node fires an over-large setTimeout immediately) |
| 2026-11-26 | On both relayer paths a success passes on only a 64-hex transaction hash and a plain id (letters, digits, `-`, `_`), rebuilt from those fields | Adversary r3f: the Channels path forwarded whatever text Channels (or a wrong `CHANNELS_BASE_URL`) put in `hash` and `transactionId`, and the wallet page links that hash as a confirmed payment |
| 2026-11-26 | Every wallet-creation answer that does not prove a refusal before sending (including an unreadable one) asks the person to check with Connect first. The relay checks its own setup (secret, RPC URL) before the payload, so an unusable RPC URL is "not set up" on every path. Changed expectation: the browser wallet needs an https RPC (smart-account-kit 0.10.0 refuses http and cannot be told otherwise), and says which setting to fix; the relay alone still accepts a local http RPC. "I already have a wallet" always asks for the passkey (`fresh`), never reuses a stored session | Adversary r3g: a CDN error page after submission said "try again"; an http RPC gave "try again" on payments; `.env.example` promised a local http RPC the wallet could not use; and (its suspicion, confirmed by the kit's documentation) `{ prompt: true }` reuses a stored session, which could bind the previous person's wallet to the next account |
| 2026-11-26 | Joshua's decision: an empty answer (204, 205, 304 or no body) from SDF's proxy on wallet creation is no longer passed on; it is a 502 asking the person to check with Connect before creating another wallet, like every other unclear answer. The r2d 204 test now expects that controlled answer. With an http RPC the wallet page names that setting instead of a sign-in problem | Adversary r3h: the wallet kit turns a passed-on 204 into "Relayer request failed with status 204", which invites a retry that can make a second passkey and an orphan wallet |
| 2026-11-26 | Ending a Supabase session is bounded: the browser client's requests time out after 10 s (supabase-js holds its session lock while one is in flight), and each sign-out step after 10 s, so a hung revoke still falls back to this browser or reports failure. The rate limiter starts a new window if the clock stepped back past its start. Restoring for another account disconnects the saved wallet even if storage refuses. A wallet creation the kit sent but could not see confirmed asks the person to check with Connect. A sign-in code that Supabase sends to the site root goes on to /auth/callback | Adversary r3i: a revoke that never answered left the session on a shared browser with the button spinning; a backwards clock step blocked the whole relay; refusing storage skipped the disconnect; and (its suspicions) a kit confirmation timeout invited a second wallet, and a code at the root was dropped |
